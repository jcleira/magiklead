# 02 — Devpods seed snapshot

**Type**: AFK
**Source PRD**: [../prd.md](../prd.md)
**Blocked by**: None — can start immediately

## What to build

Use the seed pipeline that already exists in `devpod/devpod.yml` and `devpod/seeds/regenerate.sh` to produce a committed snapshot of the canonical fixture. Run `devpods seed regenerate` once; commit `db.sql.gz` and `manifest.json`. From then on, `devpods up` on a fresh database auto-replays the snapshot, the 5-org / 20-person fixture appears for free, and `/leads` search returns rows on first visit.

This explicitly does **not** add any probe-and-seed step to the api entrypoint — the PRD picks the existing devpods mechanism over a custom runtime probe.

## Acceptance criteria

- [ ] `devpod/seeds/db.sql.gz` exists in the repo, generated by `devpods seed regenerate` (not hand-crafted).
- [ ] `devpod/seeds/manifest.json` exists; its `migration_hash` matches a SHA-256 of all `backend/migrations/*.up.sql` concatenated (per `regenerate.sh`).
- [ ] `devpods down --force && devpods up` lands on a database where `SELECT COUNT(*) FROM persons WHERE canonical_name LIKE '%(devpod-fixture)'` returns 20, with no manual `cmd/seed` invocation.
- [ ] `devpod/compose.yml` api entrypoint is unchanged (still `go run ./cmd/migrate && exec air`).
- [ ] `POST /api/v1/leads/search` for "VP Sales" returns rows on first visit to a fresh devpod.
- [ ] The `db.sql.gz` size is committed sanely (tens of KB ballpark — flag if it's unexpectedly large).

## Modules touched

- Devpods seed snapshot (committed artefact).

## Test prior art

- None — operational task. Verification is by row count and live search.

## Out of scope

- Lazy tenant bootstrap — see [issue #1](./01-lazy-tenant-bootstrap.md).
